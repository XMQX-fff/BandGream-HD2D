# OT2 HD-2D 港口小镇

基于 three.js 的浏览器 3D 游戏原型，画面风格参考《歧路旅人 2》(Octopath Traveler 2) 的 HD-2D 表现。

## 快速开始

```bash
npm install
npm run dev          # 开发服务器 http://localhost:5173
npm run build        # 产出 dist/
npm run preview      # 预览构建产物
```

### 三类资产的边界

这是本项目整理时最重要的一条约定：

| 位置 | 含义 | 是否发布 |
|---|---|---|
| `public/` | 运行时**真正会加载**的文件 | 是 |
| `assets-source/` | 构建工具的**输入**素材 | 否 |
| `tools/` | 开发期脚本与调试页 | 否 |

判断某个文件该放哪里的标准只有一条：**游戏运行时会不会请求它？**
会→ `public/`；不会但构建要用 → `assets-source/`；纯粹是开发工具 → `tools/`。

### 每个发布文件只能有一个生成者

这条是从一次真实事故里长出来的：`build_cast.py` 和 `import_kasumi_pet.py`
当初都往`public/assets/chars/cast.png` 写，谁后跑谁赢。清理资源时顺手跑了
一次前者，把香橙主图整个覆盖成纯 Kenney 角色图（图集 41KB → 11KB）——
**全程零报错，游戏照常运行，只是主角换了个人**，靠看截图才发现。

两条由此而来的硬约束：

1. `public/assets/chars/cast.png` **只由 `import_kasumi_pet.py` 写**。
   `build_cast.py` 的产物落在 `assets-source/preview/`。
2. 构建前跑 `npm run verify`，它在图集规格不对时直接失败。

## 渲染管线

管线顺序本身是设计的一部分，不要随意调整：

```
RenderPass
  → PosterizePass色阶量化
  → UnrealBloomPass   柔和辉光
  → TiltShiftPass     微缩景深
  → RenderPixelatedPass  像素化
  → OutputPass        tone mapping + 色彩空间
  → GradePass         split-tone / 暗角 / 颗粒
```

两条硬约束：

1. **所有逐像素运算必须在像素化之前**。它们按 `gl_FragCoord` 工作，
   放在像素化之后会让同一像素块内各像素结果不同，干净色块被打成彩色噪点。
2. **调色必须在 tone mapping 之后**。`renderer.toneMapping` 设为
   `NoToneMapping`，映射完全交给 `OutputPass` 执行 ——
   两者同时生效会做两次映射，把中高光压掉一大截，画面发灰、对比度尽失。

## 关键设计决策

### 地图尺寸参数化

`WORLD.SCALE` 是地图放大倍数的**唯一数据源**，雾、天空、海面、地面尺寸、
地面贴图 `repeat` 全部由它派生。改地图大小只改这一个值。

雾与天空用 `√SCALE` 而非 `SCALE` 缩放：雾是视觉引导参数，
应该在**看得见的范围内**起作用；线性放大会让远景永远不雾化，
HD-2D 最标志性的「远景融进背景」就没了。

### 程序化贴图

画面贴图基本全部由 `hd2dTextures.js` 用 Canvas 生成，不依赖外部 PBR 图片。
这是项目仅靠约 660KB JS 产物即可完整运行的原因。

### 确定性布局

城区用固定 seed（`20240517`）的伪随机数生成，保证每次刷新布局一致 ——
玩家能形成空间记忆，这是导航体验的根基。

### 相机避障与碰撞

`world/blockers` 列表登记所有会遮挡「相机 → 角色」视线的物体
（房子**与树**，不只是房子），由 `scene.js` 汇成单一数据源，同时喂给：

- **相机**（`core/camera.js`）：迭代求解抬升量与距离调整，让视线越过遮挡物
- **角色**（`world/character.js`）：把玩家推出实心建筑

两者必须共享同一份列表。历史上相机拿的是「只有房子」的列表、
角色完全没有碰撞，于是出现「相机认为视线通畅、实际被树挡住」的偏差。

避障有**三根杠杆**，按代价从小到大依次动用：

| 手段 | 范围 | 代价 |
|---|---|---|
| 抬升 `lift` | ≤ 0.9× 基准高 | 俯角变大 |
| 缩短 `pull` | ≥ 0.55× 基准距 | 取景变近 |
| **横移 `shiftX`** | ≤ 0.5× 基准距 | 视线变斜 |

抬升与缩短**受俯角上限 48° 强约束**：俯角 = `atan((camY-1.2)/ez)`，
抬得越高距离必须按比例拉远，否则画面退化成俯视平面地图。

横移是**唯一能解决「房子正好在角色正后方」的手段**。实测 (12,144)：
角色被挤到一栋 top=8.3 的房子旁 1.1 处，抬到 48° 上限、缩短到极限，
视线掠过房顶时 rayY 最高只有 6.75 —— 抬升与缩短两条路都已用尽。
相机固定在角色 +Z 侧，只要那个方向有房子就永远差那么一点；
横移让视线斜着从房子侧边绕过。

横移必须**同时把注视点偏移同样的量**，否则角色会在画面里横向漂出去
（看起来像镜头歪了，而不是镜头绕开了遮挡物）。同步偏移后角色恒在画面中央。

**横移必须与缩短联合，单靠横移无效。** 视线在盒子处的横向位移是
`sx · (1 - tExit)`。房子通常在角色身后不远处，此时 `tExit ≈ 0.87`，
`(1 - tExit) ≈ 0.13` —— sx 挪 17 单位，视线在房子处只横移了 2.25，
而 7.6 宽的房子需要 ≥3.6 才绕得出去，**差了一倍**。
缩短距离会让 `tExit` 变小、`(1-tExit)` 变大，横移效率显著提高：

| ez | (1-tExit) | sx=17 时的实际横移 | 够不够（需 3.6） |
|---|---|---|---|
| 34 | 0.13 | 2.25 | 不够 |
| 19 | 0.24 | 4.03 | 够 |

所以第 3 阶段对每个横移量都重新解一遍最短**合法**距离，取两者都满足的
第一个解。「合法」的判据是俯角 —— 缩短到下限且 camY 已抬到 31.5 时
俯角会到 58°，直接突破 48° 上限（实测真的发生过，飙到 54.7°）。
`updateCamera` 侧另有一道**无条件兜底校正**：这个函数绝不能返回
俯角超限的解，画面退化成俯视平面地图比被任何东西遮挡都更糟。

**横移量走一阶低通滤波。** 求解结果是离散跳变的（步长 4.08），
玩家沿街走时街边树不断进出视野，目标横移每 1~2 秒跳一次。
相机位移阻尼每帧只走 10%，直接用会让镜头横向抽搐。
滤波速率 2.5/s（接近时）与 20/s（反向时）——反向必须快，
否则会「卡在错误的一侧」持续遮挡。

俯角约束是**边界条件，不能放进迭代循环** —— 它要求「拉远」，
末尾的缩短逻辑要求「拉近」，写在同一变量上会互相拉扯、约束形同虚设。
正确做法是两阶段：先求任意可行解，再一次性投影到俯角允许的范围。

### 遮挡物登记的完整性

凡是竖直方向能挡住视线的东西都要登记，漏一类就会出现一类 bug。
两轮实测各漏了一类：

1. 只登记房子 → 沿街树冠（`Icosahedron`）同样横在视线上，
   且相机高度仍是基准值（说明避障压根没触发）。
2. 补上树之后 → 灯柱、木桶堆、长椅这些 `props.js` 里的道具
   从没被登记过，诊断日志里那条 `(无名):Box @28` 就是漏登记的路灯。

第二类不能靠「再手写一份坐标」解决 —— 那样每加一个道具就会再漏一次。
现在道具工厂用 `declareSight(g, r, top, solid)` **自我声明**遮挡体积，
`scene.js` 遍历场景统一收集。新增道具只要加这一行声明就自动生效。

`solid` 区分两种诉求：`true` 既挡视线也挡路（房子、灯柱、花坛）；
`false` 只挡视线（树、长椅 —— 玩家应该能从树下、长椅旁走过）。

## 开发工具

```bash
npm run shoot       # 截图（xvfb + headful Chromium）
npm run diagnose    # 相机视线诊断：射线检测遮挡物并列出命中对象
npm run walk        # 沿真实行走路径回归（12 个采样点）
npm run verify      # 发布产物守卫：图集规格 / public/ 内容
npm run build:cast  # 预览 Kenney 素材（不写 public/）
```

`diagnose` 是排查「角色看不见」这类问题的**唯一可靠手段** ——
包围盒的数学判定和真实渲染结果会对不上，射线打的是真实几何，结论唯一。
它需要 `?debug=nomerge` 模式才能定位到具体物体
（合并后整座城是一个巨型 mesh，射线只能报告「被合并体挡住」）。

### 固定机位 vs 真实路径

`diagnose` 用固定机位，`walk` 模拟玩家真实走动。**两个都要跑**，因为：

固定机位会测出玩家根本到不了的点。城区西北`(-30,120)`曾报 7 个遮挡，
几何验算证明那是死路 —— 那里是建筑夹缝，相机无论怎么摆都无解。
真实玩家沿街走，不会主动站进夹缝。`walk` 的 12 个采样点沿主街与横街，
结果证明主街全线通畅。

反过来 `walk` 不能取代 `diagnose`：`walk` 只告诉你「有遮挡」，
`diagnose` 才告诉你「被什么挡的」。

> 3. **静态机位测不出相机抖动。** 每个点等 15 秒采样，
>    抖动早就衰减完了。只有连续行走（密集采样相机 x）才能暴露 ——
>    本项目的横移低通滤波就是被这个测出来的。
>
> 两条测试纪律：
> 1. **别在测试运行期间改 `src/`** —— vite 热更新会重载页面，
>    角色被重置回出生点，后续采样点全测成同一个位置，
>    报告出一堆假结论。`walk` 已内置位置突变检测来挡这个。
> 2. **所有截图与诊断统一等阻尼收敛 15 秒**。`setPlayerPos` 是瞬移，
>    相机阻尼需要 10~15 秒才到位，2 秒时相机还在漂移上。

> 无头环境注意：本机没有 GPU，Chromium 必须走
> `xvfb-run` + headful + swiftshader，否则拿不到 WebGL2。
> 软件渲染下的 FPS 不代表真实设备表现，应关注 draw call / 三角面 / pass 耗时。
