# OT2 HD-2D 港口小镇

基于 three.js 的浏览器 3D 游戏原型，画面风格参考《歧路旅人 2》(Octopath Traveler 2) 的 HD-2D 表现。

## 快速开始

```bash
npm install
npm run dev          # 开发服务器 http://localhost:5173
npm run build        # 产出 dist/
npm run preview      # 预览构建产物
```

### 三类资产的边界

这是本项目整理时最重要的一条约定：

| 位置 | 含义 | 是否发布 |
|---|---|---|
| `public/` | 运行时**真正会加载**的文件 | 是 |
| `assets-source/` | 构建工具的**输入**素材 | 否 |
| `tools/` | 开发期脚本与调试页 | 否 |

判断某个文件该放哪里的标准只有一条：**游戏运行时会不会请求它？**
会→ `public/`；不会但构建要用 → `assets-source/`；纯粹是开发工具 → `tools/`。

### 每个发布文件只能有一个生成者

这条是从一次真实事故里长出来的：`build_cast.py` 和 `import_kasumi_pet.py`
当初都往`public/assets/chars/cast.png` 写，谁后跑谁赢。清理资源时顺手跑了
一次前者，把香橙主图整个覆盖成纯 Kenney 角色图（图集 41KB → 11KB）——
**全程零报错，游戏照常运行，只是主角换了个人**，靠看截图才发现。

两条由此而来的硬约束：

1. `public/assets/chars/cast.png` **只由 `import_kasumi_pet.py` 写**。
   `build_cast.py` 的产物落在 `assets-source/preview/`。
2. 构建前跑 `npm run verify`，它在图集规格不对时直接失败。

## 渲染管线

管线顺序本身是设计的一部分，不要随意调整：

```
RenderPass
  → PosterizePass色阶量化
  → UnrealBloomPass   柔和辉光
  → TiltShiftPass     微缩景深
  → RenderPixelatedPass  像素化
  → OutputPass        tone mapping + 色彩空间
  → GradePass         split-tone / 暗角 / 颗粒
```

两条硬约束：

1. **所有逐像素运算必须在像素化之前**。它们按 `gl_FragCoord` 工作，
   放在像素化之后会让同一像素块内各像素结果不同，干净色块被打成彩色噪点。
2. **调色必须在 tone mapping 之后**。`renderer.toneMapping` 设为
   `NoToneMapping`，映射完全交给 `OutputPass` 执行 ——
   两者同时生效会做两次映射，把中高光压掉一大截，画面发灰、对比度尽失。

## 关键设计决策

### 地图尺寸参数化

`WORLD.SCALE` 是地图放大倍数的**唯一数据源**，雾、天空、海面、地面尺寸、
地面贴图 `repeat` 全部由它派生。改地图大小只改这一个值。

雾与天空用 `√SCALE` 而非 `SCALE` 缩放：雾是视觉引导参数，
应该在**看得见的范围内**起作用；线性放大会让远景永远不雾化，
HD-2D 最标志性的「远景融进背景」就没了。

### 程序化贴图

画面贴图基本全部由 `hd2dTextures.js` 用 Canvas 生成，不依赖外部 PBR 图片。
这是项目仅靠约 660KB JS 产物即可完整运行的原因。

### 确定性布局

城区用固定 seed（`20240517`）的伪随机数生成，保证每次刷新布局一致 ——
玩家能形成空间记忆，这是导航体验的根基。

### 相机避障与碰撞

`world/blockers` 列表登记所有会遮挡「相机 → 角色」视线的物体
（房子**与树**，不只是房子），由 `scene.js` 汇成单一数据源，同时喂给：

- **相机**（`core/camera.js`）：迭代求解抬升量与距离调整，让视线越过遮挡物
- **角色**（`world/character.js`）：把玩家推出实心建筑

两者必须共享同一份列表。历史上相机拿的是「只有房子」的列表、
角色完全没有碰撞，于是出现「相机认为视线通畅、实际被树挡住」的偏差。

避障有**三根杠杆**，但**优先级不是按代价排的** —— 这一点改错过一次，
而它正是「镜头频繁跳俯角」的唯一根因：

| 杠杆 | 改变俯角？ | 观感代价 | 使用顺序 |
|---|---|---|---|
| **横移 `shiftX`** | 否 | 镜头平移，构图略歪 | **第 1** |
| **缩短 `pull`** | 否 | 镜头推近，角色变大 | **第 2** |
| 抬升 `lift` | **是** | 视角变陡，退化成鸟瞰 | **最后** |

**为什么这个顺序不能反。** 用户反馈是「遇到建筑群时不用频繁切换到低视角」，
实测俯角在 24.6° 与 48.1° 之间以约 2Hz 反复跳变。根因不是抬升量太大，
而是**抬升被当成了主力杠杆**：三根杠杆里只有它改变俯角，
一旦「先用抬升、抬满了才缩距、都不行才横移」，
就等于**每一次遮挡都直接变成一次俯角变化**。
滤波只能把「跳变」变成「快速滑动」，治不了「频繁发生」。

正确做法是加一个**第 0 阶段**：先在俯角恒为基准值的前提下，
穷举 `(shiftX, pull)` 的组合（约 120 组），取代价最小的可行解。
横移 + 缩距的可解空间很大，实测绝大多数遮挡在这一步就解开了 ——
**俯角一格不动**。只有这个空间里真的无解，才进入抬升逻辑。

代价函数用归一化加权：`|sx|/maxShift + 0.55 × 缩距比例`。
横移权重更高，因为构图歪比角色变大更明显。

抬升与缩短**受俯角上限 48° 强约束**：俯角 = `atan((camY-1.2)/ez)`，
抬得越高距离必须按比例拉远，否则画面退化成俯视平面地图。

**三个通道都要低通滤波 + 迟滞。** 之前只有 `shiftX` 有滤波，
`lift`/`pull` 是离散求解值直接施加 —— 街边树每 0.4 秒进出一次视线，
俯角就每 0.4 秒跳一次。现在三者统一走一阶低通：

- 升（跟随目标）7.0/s —— 玩家要立刻看清角色被挡在哪
- 降（回到基准）1.6/s —— 快速回落是抽搐的另一半来源
- **迟滞 0.35 秒** —— 遮挡消失后必须连续通畅 0.35 秒才开始回落。
  抖动周期约 0.5 秒，这个保持窗让升降连不成一个完整周期。
  效果是「走过一排树时抬升一直保持（画面稳定，只是偏高一点）」，
  与 OT2 的镜头行为一致，而不是在每棵树前面点一下头。

横移速率 2.5/s（接近）与 2.0/s（下降）。它必须**同时把注视点偏移同样的量**，
否则角色会在画面里横向漂出去（看起来像镜头歪了，而不是镜头绕开了遮挡物）。
同步偏移后角色恒在画面中央。

**横移必须与缩短联合，单靠横移无效。** 视线在盒子处的横向位移是
`sx · (1 - tExit)`。房子通常在角色身后不远处，此时 `tExit ≈ 0.87`，
`(1 - tExit) ≈ 0.13` —— sx 挪 17 单位，视线在房子处只横移了 2.25，
而 7.6 宽的房子需要 ≥3.6 才绕得出去，**差了一倍**。
缩短距离会让 `tExit` 变小、`(1-tExit)` 变大，横移效率显著提高：

| ez | (1-tExit) | sx=17 时的实际横移 | 够不够（需 3.6） |
|---|---|---|---|
| 34 | 0.13 | 2.25 | 不够 |
| 19 | 0.24 | 4.03 | 够 |

第 0 阶段对每个横移量都重新解一遍最短**合法**距离，取两者都满足的
第一个解。「合法」的判据是俯角 —— 缩短到下限且 camY 已抬到 31.5 时
俯角会到 58°，直接突破 48° 上限（实测真的发生过，飙到 54.7°）。
`updateCamera` 侧另有一道**无条件兜底校正**：这个函数绝不能返回
俯角超限的解，画面退化成俯视平面地图比被任何东西遮挡都更糟。

俯角约束是**边界条件，不能放进迭代循环** —— 它要求「拉远」，
末尾的缩短逻辑要求「拉近」，写在同一变量上会互相拉扯、约束形同虚设。
正确做法是两阶段：先求任意可行解，再一次性投影到俯角允许的范围。

**空间网格。** 城区登记 552 个遮挡物，第 0 阶段要试约 120 组组合，
全量遍历就是 148 × 552 ≈ 8.2 万次盒判定/帧（约 1.6ms）——
它吃的是渲染帧预算，低端机上会直接掉帧。
但真正能挡住视线的只有「相机与角色之间」那几个盒子，
也就是 Z 落在 `[targetZ, targetZ+baseDist]` 这一条带里的（地图跨 280 单位，
只占约 12%）。按 Z 分桶（边长 16）后每次只扫几十个，开销降到 1/8 以下。
桶挂在 blockers 数组自身的 Symbol 属性上，同一个列表只构建一次。

### 遮挡物登记的完整性

凡是竖直方向能挡住视线的东西都要登记，漏一类就会出现一类 bug。
两轮实测各漏了一类：

1. 只登记房子 → 沿街树冠（`Icosahedron`）同样横在视线上，
   且相机高度仍是基准值（说明避障压根没触发）。
2. 补上树之后 → 灯柱、木桶堆、长椅这些 `props.js` 里的道具
   从没被登记过，诊断日志里那条 `(无名):Box @28` 就是漏登记的路灯。

第二类不能靠「再手写一份坐标」解决 —— 那样每加一个道具就会再漏一次。
现在道具工厂用 `declareSight(g, r, top, solid)` **自我声明**遮挡体积，
`scene.js` 遍历场景统一收集。新增道具只要加这一行声明就自动生效。

`solid` 区分两种诉求：`true` 既挡视线也挡路（房子、灯柱、花坛）；
`false` 只挡视线（树、长椅 —— 玩家应该能从树下、长椅旁走过）。

### 建筑遮挡淡出（dither discard）

玩家抱怨「角色走到建筑后面就看不见了」。相机避障能解掉大部分，
但解不掉的那些（贴墙、高墙）需要建筑自己让开。

**为什么不用 `opacity`。** 两条独立的死因：

1. 材质是**全局共享**的 —— `props.js` 缓存材质，全城上千栋房子的墙
   共用一个 `MeshStandardMaterial`。调低 opacity = 全城的墙一起变透明。
2. 真alpha 混合要开 `transparent + depthWrite=false`，
   半透明物体间**失去深度排序**；而且本项目管线末端的
   `RenderPixelatedPass` 靠 depthTexture 做描边，
   半透明物体不写深度 → 房子淡出后轮廓也没了，
   画面读作「房子凭空消失」而不是「房子变透明」。

**为什么按 `(材质, 栋)` 分桶也是错的。** 第一反应是改`optimize.js` 让它按
`(material, fadeGroup)` 分桶，这样「一栋楼 = 一组可独立控制的 mesh」。
但全城上千栋 × 每栋 4~6 种材质 ≈ 4000~6000 个 mesh，
而优化前只有几十个 —— **draw call 涨两位数**。
本项目瓶颈完全在 CPU 端提交（分辨率降到 1/16 帧率几乎不变），
为一个视觉增强把帧率打掉两个数量级不可接受。

**最终方案：逐顶点 `aFadeId` + 抖动剔除。**

- 合并时给每个顶点附带 `aFadeId`（该顶点属于哪栋楼），
  **合并的分桶逻辑完全不变** —— 同一个合并 mesh 里装着几百栋楼的顶点，
  各自带不同的 id。draw call 与优化前**完全一致**（实测 19038 → 1133）。
- 材质用 `onBeforeCompile` 注入一小段 shader：按 `aFadeId` 查一张
  1×2048 的查找表得到保留率，用 4×4 Bayer 矩阵与保留率比较，
  决定这个片元 `discard` 还是保留。
- 每帧只更新查找表里的几个字节，不重建几何、不重编译 shader。

选`discard` 而非 alpha 混合的好处：深度缓冲始终正确，
像素化 pass 的描边照常工作，**房子淡出后轮廓还在**；
抖动网格与 `PIXEL_SIZE=3` 的像素块对齐，半透明区呈现规整点阵 ——
这正是 HD-2D 像素风的原生语言，不是将就。

**组号的唯一来源是 `blockers` 数组下标。** 曾设计过在
`buildingTypes.js` 里自增一个 `FADE_ID`，但那是**第二套需要与
`BLOCKERS` 保持同步的编号** —— 一旦错位就是**静默错淡**：
查到隔壁那栋的保留率，画面上却把这栋淡掉了，
没有报错、没有日志，只有肉眼觉得「怪」。
现在 `registerBlocker` 返回 `idx = BLOCKERS.length`，
几何体的 `aFadeId` = blockers 下标 = 淡出查表下标，三方共用一个编号。

`customProgramCacheKey` 是必需的：`onBeforeCompile` **不参与** three 的
程序缓存键哈希，未设置时「注入了淡出」和「没注入」的材质若参数恰好相同
会共用同一 program，注入静默失效 —— 症状是淡出时好时坏，取决于材质被谁先编译。

**两条判据取并集。** 只判「视线被挡」实测几乎从不触发
（camera.js 的三杠杆避障已经把绝大多数遮挡解开了）。
玩家说的「被挡住看不见」更多是**角色贴在建筑侧面**——
视线从房子旁边擦过去没被挡，但房子在画面里与角色重叠。
实测贴墙点比视线遮挡多一个数量级，所以判据 B 用
**投影重叠**（把盒子与角色一起投到垂直于视线的平面上）
而不是「min(dx,dz) 很小」——后者会把侧向的房子也淡掉。

判据 B 还必须有**距离上限**：投影重叠只说明左右对齐，
还需要上下对齐。相机俯角约 34.7°，射线朝相机方向每远 1 单位升高 0.693，
所以 17 米外一栋 7 米的矮楼在屏幕上位于角色脚边远处，根本盖不住角色。
缺了这条会同时淡出 13 栋（实测），画面碎成筛子。补上后降到最多 5 栋，
全城 3695 个可达采样点里只有 5 个超过 3 栋。

### 本轮修掉的三个真实 bug

这三个都是**之前一直存在、但被「只统计数量」的诊断掩盖**的问题。

**1. 遮挡盒全部登记在 (0,0)。**
`city.js` 的 `makeBuilding` 先 `type.make(0, 0)` 再 `g.position.x = ...`，
而 `buildingTypes.js` 的 `finish()` 在 `make()` 内部就调
`declareBuildingSight(x, z, ...)` 登记遮挡盒 —— 那一刻坐标还是 0。
于是**每一栋沿街建筑的碰撞盒都在世界原点**，
之后Group 移到真实位置而盒子不会跟着走。
实测 1170 个盒子里777 个中心恰好是 (0,0)。

影响远不止淡出：碰撞（`character.js`）读同一份盒子 → **房子撞不到**，
玩家能穿过所有建筑；相机避障（`camera.js`）同样读它 → 一直在躲原点的假墙。
修法是**先算最终坐标再 `make()`**，而不是事后回填盒子 ——
回填时一旦漏掉某条路径就变成「盒子与组号不匹配」的静默错淡。

**2. 一条横街整条建在地图外。**
`CROSS_Z` 含 210，街道被推到 z = 244，而城区上界 `B.maxZ = 240`。
那排建筑玩家根本看不到，却照样登记碰撞盒与淡出组号。
它同时是「压路」判定唯一的失败项，把排查引向「偏移公式算错了」这个错误方向。

**3. 判据 B 没有距离上限**（见上一节）。

前两个之所以一直没被发现：**所有诊断都只统计「数量」**，
而数量是对的 —— 777 个盒子确实存在，只是都在错的地方。
是新增的「盒子坐标 vs 建筑标签坐标」交叉校验才暴露出来的。

### 街区布局：从「贴满」到「有形态」

上一轮把「贴住率 66~68%、断口 0」当优化目标，结果矫枉过正：
每个地块四边贴满、墙缝只有 0.8、地块之间只内缩 3.4（背靠背又是连续一堵墙）、
所有街区形态完全相同 → 读作「一堵 200 米长、每 20 米重复一次的墙」。

关键认知：**贴住率根本不是「密集」的正确度量**。
它只沿主街量（`zone='main'`），而「太密集」发生在街区内部（`zone='perimeter'`）。

现在按坐标哈希（不是随机数，保证可复现）把地块分成三种形态：

| 形态 | 边数 | 内缩 | 墙缝 | 原型 |
|---|---|---|---|---|
| `dense` | 四边全排 | 3.0 | 0.55 | 老城核心联排 |
| `sparse` | 缺一条边 | 4.2 | 1.25 | 住宅外围，有前院 |
| `civic` | 只排一边 | 5.2 | 2.0 | 广场/教堂前开阔地 |

**缺一条边比排稀一点更重要** —— 排稀只是房子之间有空隙，
街区轮廓仍是完整矩形，玩家看到的还是「一个塞满的方块」；
缺边才形成 L 形/U 形开口，视线能穿进地块内部，
于是有了「巷子」和「院子」的读法。`civic` 同时是玩家的呼吸空间。

巷口节奏也从每 3~5 栋放宽到 2~4 栋、宽度 4.0 → 5.0：
巷口是斜俯视游戏里唯一能看穿街区的开口。

`tools/city_report.py` 新增的**街区密度分布**指标负责验收：
变异系数 0.44（`cv < 0.25` 会报警「读作重复纹理而非城市」）、
空地块 0 个、过密地块 0 个 —— 三种形态确实产生了起伏。

### 测试机位必须由代码选，不能手写

本轮在这个问题上栽了三次同样的跟头，值得单独立一条：

| 错误输入 | 测出来的假象 |
|---|---|
| `setPlayerPos` 只挪角色，相机仍在阻尼途中 | 「淡出完全没生效」 |
| 手写机位坐标，布局改版后落在空地| 「淡出完全没生效」 |
| 手挑「看起来空旷」的基准，实际紧邻民居 | 「空旷处也误淡」 |

共同点：**用不具代表性的输入验证系统，然后差点责怪系统**。
判定逻辑本身三次都是对的。

所以现在：`fade_scan.py` 逐点调 `fadeProbe()`全城扫描，
按明确判据（可达 + 会触发 + 触发数适中 + 在可玩城区内）
推荐测试机位与空旷基准点，`fade_probe.py` 直接用扫描结果。
布局再改版也不用重挑坐标，重跑一次扫描即可。

两个配套的确定性保障：

- **`teleport` 钩子**（瞬移 + `snapCamera` 立即落位）——
  软渲染只有 1 fps，靠「等 N 秒等阻尼收敛」不可靠。
- **`fadeReset` 钩子** —— 恢复速率 3.0/s而 dt 钳在 0.05，
  1 fps 下要 9 秒以上才恢复得完。不复位的话，
  基准机位测到的是上一个机位的残留，看起来像误淡。

`diagnose` 是排查「角色看不见」这类问题的**唯一可靠手段** ——
包围盒的数学判定和真实渲染结果会对不上，射线打的是真实几何，结论唯一。
它需要 `?debug=nomerge` 模式才能定位到具体物体
（合并后整座城是一个巨型 mesh，射线只能报告「被合并体挡住」）。

### 固定机位 vs 真实路径

`diagnose` 用固定机位，`walk` 模拟玩家真实走动。**两个都要跑**，因为：

固定机位会测出玩家根本到不了的点。城区西北`(-30,120)`曾报 7 个遮挡，
几何验算证明那是死路 —— 那里是建筑夹缝，相机无论怎么摆都无解。
真实玩家沿街走，不会主动站进夹缝。`walk` 的 12 个采样点沿主街与横街，
结果证明主街全线通畅。

反过来 `walk` 不能取代 `diagnose`：`walk` 只告诉你「有遮挡」，
`diagnose` 才告诉你「被什么挡的」。

> 3. **静态机位测不出相机抖动。** 每个点等 15 秒采样，
>    抖动早就衰减完了。只有连续行走（密集采样相机 x）才能暴露 ——
>    本项目的横移低通滤波就是被这个测出来的。
>
> 两条测试纪律：
> 1. **别在测试运行期间改 `src/`** —— vite 热更新会重载页面，
>    角色被重置回出生点，后续采样点全测成同一个位置，
>    报告出一堆假结论。`walk` 已内置位置突变检测来挡这个。
> 2. **所有截图与诊断统一等阻尼收敛 15 秒**。`setPlayerPos` 是瞬移，
>    相机阻尼需要 10~15 秒才到位，2 秒时相机还在漂移上。

### 俯角跳变：为什么静态机位测不出来

俯角跳变是**帧与帧之间**的现象。任何「在某个瞬间读一次俯角」的诊断都测不到它 ——
读到多少完全取决于你在跳变的哪个相位上采样。
所以 `walk` / `diagnose` 这类「等15 秒收敛后读一个值」的测试，
在这个问题上**结构性地无效**。

`tools/pitch_probe.py` 为此从外部注入一个 rAF 探针，逐帧记录俯角时间序列，
再看**摆幅**（max-min）与**单帧最大跳变**。判定阈值：
摆幅 ≤ 6°、单帧 ≤ 1.2°/帧（**后者需按帧率归一化**，见下）。

> **单帧阈值必须按 dt 归一化，否则低帧率下必然误判。**
>
> 相机对 lift/pull 走的是一阶低通 `prev + (t-prev)*(1-e^(-RISE·dt))`，
> 所以「单帧最多能变多少」完全由 `dt` 决定：
>
> | 帧率 | dt | 滤波允许的单帧俯角变化（跨 6°） |
> |---|---|---|
> | 1.2 fps（实测软渲染） | 863 ms | 6.0° |
> | 5 fps | 200 ms | 4.52° |
> | 10 fps | 100 ms | 3.02° |
> | 30 fps | 33 ms | 1.25° |
> | **60 fps** | 16.7 ms | **0.66°** |
>
> 本机软渲染实测只有 **1.2 fps**（平均帧间隔 863 ms），
> 滤波**本身就允许**单帧走 6°。用固定阈值 1.2° 去判必然 FAIL，
> 而且会诱导人去改相机的滤波参数 ——
> 那才是真正的破坏：**把画面调卡来迁就测试**。
> 所以探针会记录平均帧间隔，按 `SPAN*(1-e^(-RISE·dt)) * 1.15` 算出门槛，
> 真实 60 fps 设备上门槛仍是 1.2°，不会被放宽成永远 PASS。
>
> 换句话说：**软渲染下测出的「单帧跳变」没有参考价值，只有摆幅与跳变次数有意义。**
> 摆幅 5.9° 是与帧率无关的量，它达标才是真的达标。

> 写这个探针时踩了三个坑，每一个都会产出**看起来合理但完全无效**的结论。
> 它们的共同特征是：失败时不会报错，只会安静地给出一份好数据。
>
> 1. **不能用「Python 逐次 evaluate」当帧驱动。**
>    一次 evaluate 不等于一个渲染帧 —— evaluate 是 CDP 往返，耗时几毫秒到几十毫秒，
>    而 rAF 按真实时钟走。实测 34 秒里页面只渲染了几十帧，evaluate 却调了 260 次。
>    正确做法：把「推进角色 + 记录俯角」放进**同一个 rAF 回调**，
>    页面按自己的帧节奏走完 N 帧，Python 只等它结束。
> 2. **行程不能越过地图边界。**
>    第一版每段走 200 帧 × 0.55 单位 = 110 单位，起点都是 z=30，
>    终点全部落在 z≈-80 —— 已越过北界（B.minZ≈-40）。
>    越界后 `setPlayerPos` 被 clamp，角色不再移动，俯角自然恒定，
>    于是报出「摆幅 0.1°、0 次跳变」的**完美平滑**结果。
>    现在每段 70 帧 × 0.5 单位、起点错开分布，并内置**位移量断言**
>    （移动不足 8 单位即判本次数据无效）。
> 3. **必须掐掉起步的阻尼暂态。**
>    `setPosition` 是瞬移，相机阻尼要 10 秒才收敛。
>    起步十几帧的俯角从瞬移值往基准值快速滑动（实测 29.12° → 23.47°，跨度 5.6°），
>    那是收敛过程、不是避障跳变。不掐掉会把暂态误判成 FAIL。
>
> 通用教训：**任何「测出来好得可疑」的数据都要先验证测量本身**。
> 探针必须自证「确实测到了它声称测的东西」——位移断言、帧数下限都是为此。

### 俯角问题：三个被误诊的根因

修这个问题的过程里，我先后**三次**把原因判断错了。
三个错误的共同点：都在「相机为什么必须抬升」这一层找答案，
而真正的原因在更前面 —— **世界模型本身是错的**。

记录在此，因为它们都属于「不会报错、只会让画面慢慢变怪」的类别。

> 1. **树冠被当成实心高墙。**
>    街边树登记遮挡时写的是 `registerBlocker(x, z, spread*3.2, spread*3.2, h, false)`。
>    spread 最大的树 → 登记盒 **10.9 × 10.9、高 7.5**。
>    于是一棵树在视线里就是一堵 11 米宽的墙，沿街一排树直接组成连续遮挡墙，
>    第 0 阶段（横移 + 缩距）必然无解 → 退到抬升兜底 → 俯角冲到 48°。
>    而 `solid = false` 并不代表它不挡相机：**遮挡判定根本不看 `solid`**，
>    那个字段只管角色能不能穿过去。
>    树冠是透空的球簇，视线穿过缝隙在视觉上完全可接受，
>    现在只登记树干那一段：`registerBlocker(x, z, 0.7, 0.7, 2.6, false)`。
>
> 2. **巷口计数与建筑序号共用变量，导致整条街死循环。**
>    巷口判定写成 `if (n % (3 + rng()*2) === 0) { cursor += 4; continue; }`。
>    巷口分支里 `n` 不变，于是每轮拿同一个 `n` 再掷一次 `p`。
>    **当 `n` 同时是 3 和 4 的公倍数（n = 12、24…）时，
>    `n%3==0` 且 `n%4==0`，`p` 无论掷出 3 还是 4 都命中 → 永远命中 → `n` 永不推进。**
>    症状极具迷惑性：`while (cursor < to)` 仍在跑（光标每次挪 4），
>    所以不报错、不卡死，只是主街只排出 12 栋就再没有建筑，
>    z 停在 78而范围明明到 230 —— 表现为「后面 150 米一条街全是空地」。
>    修法是让巷口用**独立计数** `alleySince`，与建筑序号彻底解耦。
>
> 3. **避障求解与阻尼插值不一致，判定的不是画出来的那条视线。**
>    `solveSightline` 用角色的**当前**位置算视线，
>    但相机随后还要 `lerp(desired, k)` —— **相机是滞后的**。
>    于是求解器判断「通畅」时算的是理想位置的视线，
>    真正渲染的那一帧相机还停在半路上，视线扫过的位置完全不同。
>    实测证据很干净：**同一位置静止时俯角 24.89°，移动中却升到 34.66°**。
>    同一位置、同一遮挡、差 10°，差的那部分全部来自阻尼滞后。
>    修法：把注视点按同一阻尼系数前移一帧，用前移后的点求解，
>    让「算的」与「画的」是同一条视线。
>
> 这三条的共同教训：**画面不对时，先怀疑世界模型，再怀疑求解器。**
> 求解器层面的滤波只能平滑症状；世界模型错了，滤波就是把错误画得更好看。

### 诊断脚本本身也是被测对象

`tools/city_report.py` 出过一次「极具说服力的错误结论」：

```
类型分布：cottage 79.2% / warehouse 17.9% / 其余 5 种均为 0
```

看起来像「新建筑类型根本没生效」。实际是**反推规则错了**：
它靠登记盒的进深反推类型，而登记盒含出挑与院墙 ——
带院独栋主体进深 4.0、登记盒却是 5.92，被误判成 warehouse（进深 5.0）；
杂物棚进深 2.0 落在 cottage 的容差范围内，被直接吞掉。
**几何反推在有出挑/院墙/旋转时永远不可靠。**

改法是让类型由工厂自己报出来（`tagBuilding` → `exportBuildingTags`），
诊断脚本只做统计。同一份数据，改完之后 9 种类型全部出现、分布合理。

> 同一个脚本还有一处错误：算沿街间隙时把**横街**建筑混进了主街序列。
> 横街整排的 z 恒定、只有 x 在变，混进去立刻算出「中位间隙 -1.90」
> （负值 = 建筑重叠），看着像联排彻底崩了。
> 天际线连续性**只能取 `zone === 'main'`**。
>
> 教训同上：诊断工具的输出必须先自证口径正确，再去解释被诊断的对象。

> 无头环境注意：本机没有 GPU，Chromium 必须走
> `xvfb-run` + headful + swiftshader，否则拿不到 WebGL2。
> 软件渲染下的 FPS 不代表真实设备表现，应关注 draw call / 三角面 / pass 耗时。
> 实测软渲染只有**约 1.2 fps**（平均帧间隔 863 ms），
> 所以逐帧探针一次要跑十几分钟 —— 采样段数不要开太大。
